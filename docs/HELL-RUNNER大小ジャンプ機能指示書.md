# HELL RUNNER 大ジャンプ・小ジャンプ機能 実装指示書

作成日: 2026-08-16  
状態: **実装前。別AIへ渡せる確定仕様**

## 1. 目的

現在の「押した瞬間に常に同じ高さまで跳ぶ」操作へ、押している長さで高さが変わる可変ジャンプを追加する。

- 短く押す: 小ジャンプ
- 押し続ける: 現在と同じ大ジャンプ

小さな段差やコイン列を細かく狙えるようにしつつ、既存の奈落・段差・2段ジャンプ・3段ジャンプ・滑空を壊さないことを最優先とする。

## 2. 採用方式

ジャンプ開始時の速度は、現在と同じ `-JUMP_VELOCITY` を与える。

上昇中にボタンを離した場合だけ、上向き速度を弱めて早めに頂点へ移行させる「ジャンプカット方式」を採用する。

概念例:

```js
if (jumpReleased && player.vy < 0) {
  player.vy *= jumpReleaseCut;
}
```

理由:

- 最大ジャンプは現状と同じ軌道を維持できる
- 地形生成が参照する `JUMP_VELOCITY`、`SINGLE_JUMP_APEX`、奈落幅を変更せずに済む
- 押した瞬間から反応するため、長押し時間を待ってから跳ぶ方式より操作遅延がない
- PCのキー入力と携帯のタップを同じ処理へ統一できる

## 3. 操作仕様

### 1段目

- pointerdown / Space / ↑ / W のkeydownで、従来どおり即座にジャンプする
- 上昇中にすぐ離すと小ジャンプ
- 押し続けると現在と同じ最大高度の大ジャンプ
- 頂点を越えて落下へ入った後に離しても軌道を変えない

### 2段目・3段目

- 空中で再度押した瞬間に、従来どおり次のジャンプを発動する
- 2段目と、レッドブル選択時の3段目にも同じ大小判定を適用する
- 新しいジャンプを開始するたび、そのジャンプ専用の押下状態へ切り替える
- 1段目のボタンを押し続けただけで2段目を自動発動させない

### 滑空

- 滑空の既存条件「滑空能力を持ち、落下中に入力を押し続けている」を維持する
- 同じ長押し操作が、上昇中は大ジャンプ、落下中は滑空として自然につながる
- 小ジャンプ後に滑空したい場合は、一度離して小ジャンプを確定し、落下中にもう一度押す
- 滑空の重力倍率 `0.32` は今回変更しない
- 可変ジャンプの追加を理由に、滑空能力の解放距離・選択仕様を変更しない

## 4. 初期調整値

最終値はデバッグモードの実機試遊で決める。最初の候補値は以下。

| 項目 | 初期候補 | 意味 |
|---|---:|---|
| 最大ジャンプ速度 | 現在の `JUMP_VELOCITY` | 大ジャンプと既存地形を維持 |
| リリースカット率 | `0.55` | 上昇中に離した瞬間、残り上向き速度を55%へ縮小 |
| 最低カット受付時間 | `0.04秒` | 誤タップや同フレームreleaseによる極端な低ジャンプを防止 |
| 最大ジャンプ到達扱い | `0.18秒` | これ以上押していればrelease時にカットしない目安 |

目標感触:

- 小ジャンプの頂点は大ジャンプのおよそ55～65%
- 大ジャンプの高さ・滞空時間・到達距離は現状から変えない
- 軽いタップでも小さすぎて最初の段差へ引っかからない
- 携帯Safariでタップ時間のばらつきがあっても大小を意図的に出し分けられる

注意: 高さは速度の二乗に比例するため、カット率と実際の高さ比は同じにならない。数値だけで決めず、必ず実機で確認する。

## 5. 状態管理

新しく最低限、以下に相当する状態を持つ。

- `jumpHeldTime`: 現在のジャンプ開始後に入力を押していた時間
- `jumpCanBeCut`: 今の上昇へリリースカットを一度だけ適用できるか
- `jumpReleaseQueued`: pointerup / keyupを物理更新へ安全に渡すフラグ

ジャンプ開始時:

1. `player.vy = -JUMP_VELOCITY`
2. `jumpHeldTime = 0`
3. `jumpCanBeCut = true`
4. `jumpReleaseQueued = false`

押している間:

- `state === 'playing'` のときだけ `jumpHeldTime` を増やす
- 一時停止、復活カウント、再開カウント中は増やさない

離した時:

- `jumpCanBeCut === true`
- `player.vy < 0`
- 最低カット受付時間を経過済み
- 最大ジャンプ到達扱いの時間より前

上記をすべて満たす場合だけ、一度だけ上向き速度をカットする。その後 `jumpCanBeCut = false` にする。

次の場合もカット権を終了する。

- 頂点へ到達して `player.vy >= 0` になった
- 着地した
- 次の空中ジャンプを開始した
- 死亡、転生、デバッグ復帰、ゲーム開始、TOPへ戻る

## 6. 入力イベント

既存の入力方式を維持する。

- `pointerdown`: `holdingInput = true`、従来の `requestJump()`
- `pointerup`: `holdingInput = false`、ジャンプリリースを予約
- `pointercancel`: pointerupと同じ扱い
- `keydown`: Space / ↑ / W。キーリピートでジャンプ回数を消費しない
- `keyup`: 対応キーを離したらジャンプリリースを予約
- `touchstart` / `touchmove` の既存 `preventDefault()` を壊さない

追加注意:

- ボタン、リンク、デバッグUI、一時停止UIの操作をジャンプへ混ぜない
- ウィンドウが非表示になった場合は入力を解除し、復帰直後に大ジャンプ・滑空が残らないようにする
- 一時停止機能が先に実装されている場合、`paused` と `pauseCountdown` 中の入力を無視する
- 一時停止機能がまだ未実装でも、後から統合しやすいよう入力解除処理を関数化する

## 7. 地形・難易度を維持する条件

- `JUMP_VELOCITY` と `GRAVITY` の本番初期値は変更しない
- `SINGLE_JUMP_APEX` と奈落生成上限を変更しない
- 既存の単発ジャンプ・2段ジャンプで到達可能だった地形は、大ジャンプ操作で引き続き到達可能にする
- 小ジャンプを必須にしない。小ジャンプは操作精度を上げる追加手段とする
- 大ジャンプを最大まで出すために不自然な長押しを要求しない
- ライバルAIのジャンプは現状の固定ジャンプを維持する。プレイヤー用のリリースカットを適用しない
- コイン配置や能力解放条件は今回変更しない

## 15. レビュー結果（2026-08-16 コード実測）

実装前に既存コードと突き合わせた。**方式（ジャンプカット）は妥当で、符号の扱いも正しい。**
ただし4節の数値仕様に、意図と逆の結果を生む欠陥がある。以下を反映してから着手すること。

### 15.1 【重大】「最低カット受付時間」が、速いタップほど大ジャンプにしてしまう

5節は「離した時に**最低カット受付時間を経過済み**」をカット適用の条件にしている。
つまり `0.04秒` より早く離すと**カットされず最大ジャンプになる**。
これは3節「上昇中にすぐ離すと小ジャンプ」と正面から矛盾する。

さらに実装上、この欠陥はほぼ確実に踏む。**ジャンプはイベントハンドラでは発動しない。**

```js
// pointerdown / keydown 側はフラグを立てるだけ
function requestJump(){
  if(state === 'playing'){ jumpQueued = true; }
}
```

実際の発動は `update()` 内（`if(jumpQueued){ ... player.vy = -JUMP_VELOCITY; ... }`）で、
**次フレームまで遅れる**。素早いタップでは `pointerup` がジャンプ開始前後に来るため、
「押していた時間」は事実上0になり、**必ず0.04秒を下回る＝カットされない**。

結果、**タップが速いほど大きく跳ぶ**という壊れた操作感になる。

**修正案（推奨）: 「最低時間未満はカットしない」をやめ、「常にカットし、高さの下限で守る」へ変える。**

```js
// 離したら必ずカットする。ただし極端に低くなりすぎないよう下限を設ける。
// (vyは負が上昇。より負の値が速い上昇なので Math.min が「下限速度」になる)
player.vy = Math.max(player.vy, Math.min(player.vy * JUMP_RELEASE_CUT, -JUMP_VELOCITY * JUMP_MIN_RISE));
```

`JUMP_MIN_RISE` は「最低でも初速の何割は残す」という比率。`MIN HOLD` スライダーは
**この下限比率の調整**へ役割を変える。時間ではなく比率で守るほうが、入力遅延に左右されない。

### 15.2 【重大】キーリピート対策が入っておらず、長押しが標準操作になると顕在化する

現在の `keydown` に `e.repeat` のガードが無い。

```js
window.addEventListener('keydown', (e)=>{
  if(e.key === ' ' || e.key === 'ArrowUp' || e.key === 'w' || e.key === 'W'){
    e.preventDefault();
    holdingInput = true;
    if(state === 'playing') requestJump();   // ← リピートでも毎回呼ばれる
```

OSのキーリピートは約0.5秒後に始まり、以降は毎秒数十回発火する。`jumpQueued` が毎フレーム
立つため、**2段目・3段目が自動的に消費される**。

現状は「タップ＝即最大ジャンプ」なので長押しする理由が無く、表面化しにくかった。
だが本機能では**長押しが大ジャンプの標準操作になる**。つまり
**PCで大ジャンプするたびに2段目が勝手に消える**。3節「1段目のボタンを押し続けただけで
2段目を自動発動させない」を満たすには、この既存バグの修正が必須。

```js
if(e.repeat) return;  // キーリピートでジャンプ回数を消費しないため
```

> **【対応済み】この修正は 2026-08-16 に本体へ適用済み（コミット `6013295`）。**
> 大小ジャンプとは独立した既存バグだったため先行して直した。**再実装しないこと。**
> 12節のテスト10「キーリピートでジャンプ回数を余分に消費しない」は、この挙動を
> 保証するテストとして追加すること。

### 15.3 【要判断】既存プレイヤーの操作感が変わる

実測値から計算した結果（`GRAVITY = 3400`、`JUMP_VELOCITY = 1180`）:

- 最高到達点 `SINGLE_JUMP_APEX` = **204.8px**、頂点までの上昇時間 = **0.347秒**
- 地形の段差の最大 `STEP_MAX_H` = **132px**

カット率0.55での離すタイミング別の到達高さ:

| 離す時刻 | 到達高さ | 大ジャンプ比 |
|---:|---:|---:|
| 0.04秒 | 93px | 45% |
| 0.10秒 | 132px | 65% |
| 0.18秒 | 172px | 84% |

**現在は「どんなタップでも204.8px」。変更後、軽いタップは93pxになる。**
最大段差132pxを越えられない。既存プレイヤーの指の癖はそのままなので、
**変更直後は明らかに死にやすくなる。**

7節は「小ジャンプを必須にしない」としているが、問題は必須かどうかではなく
**同じ入力が別の結果を生むこと**。以下のいずれかを検討すること。

- `FULL HOLD` を短め（0.12秒程度）にして、大ジャンプを出しやすくする
- 初回プレイ時に操作変更を知らせる
- 4節の目標値「小ジャンプは大ジャンプの55〜65%」に合わせるなら、
  上表より**離す猶予をもっと長く**取る必要がある

なお15.1の修正を入れると、0〜0.18秒が30%〜84%へ滑らかに対応する。
現行仕様のままだと**55〜65%を狙える幅が0.04〜0.10秒の約60msしかなく**、
4節が懸念している「携帯Safariのばらつき」に耐えられない。**15.1の修正はここでも効く。**

### 15.4 【構造的な衝突】大ジャンプと滑空が、どちらも「長押し」に割り当たる

滑空の既存実装:

```js
gliding = abilities.glide && holdingInput && player.vy > 0;
player.vy += GRAVITY*dt*(gliding ? 0.32 : 1);
```

`holdingInput` を見ているため、**滑空能力を持つプレイヤーが大ジャンプ（＝押し続け）をすると、
頂点を越えた瞬間に必ず滑空へ入る**。「大ジャンプしたいが滑空はしたくない」場合、
頂点で指を離す必要がある。

3節はこの流れを「自然につながる」と書いているが、**滑空持ちにとって大ジャンプと滑空を
切り分ける手段が無くなる**点は明記されていない。仕様として許容するなら、その旨を
指示書へ書き足すこと。切り分けたいなら別の入力が要る（今回の範囲を超える）。

### 15.5 【携帯】マルチタッチで意図せずジャンプがカットされる

`pointerup` は指を1本離しただけで発火し、`holdingInput = false` になる。
現状でも滑空が途切れる問題があるはずだが、可変ジャンプでは
**2本目の指を離しただけで上昇が切られる**ため、影響が大きくなる。

押されているポインタ数を数えて `holdingInput` を管理する方式を検討すること
（6節の「入力解除処理を関数化する」と合わせて対応できる）。

### 15.6 実装アンカー（確認済みの事実）

| 項目 | 実測 |
|---|---|
| 符号 | `vy < 0` が上昇、`vy > 0` が落下。**2節のコード例は正しい** |
| ジャンプ発動位置 | `update()` 内の `if(jumpQueued){...}` ブロック。**イベントハンドラではない**。`jumpHeldTime` 等の初期化はここへ置く |
| 3段ジャンプ | `maxJumpsThisRun = abilities.redbull ? 3 : 2` で実在。前提は正しい |
| 滑空の重力倍率 | `0.32` を確認。変更不要 |
| キー | `' '` / `ArrowUp` / `w` / `W` の keydown・keyup が実在 |
| ライバルAI | プレイヤーとは別処理。`holdingInput` を見ていないので、7節の「固定ジャンプ維持」は自動的に満たされる |

### 15.8 【最重要】小ジャンプの価値は「高さ」ではなく「滞空時間」にある

この機能を入れる目的は、ユーザー確認により次の2点と確定した。**どちらもコードで成立を確認済み。**

**用途1: ジャンプ回数を早く回復する**

小さな段差を大ジャンプで越えると、着地までの約0.69秒を空中で過ごす。その最中に奈落が来ると
2段目を使わされ、残弾ゼロで奈落に挑むことになる。小ジャンプなら早く着地でき、
`player.jumpsUsed = 0`（着地処理内）で**ジャンプ回数が満タンに戻ってから**奈落へ入れる。

**用途2: 飛び越しすぎを防ぎ、狙った足場へ降りる**

空中で2段目を撃つと `player.vy = -JUMP_VELOCITY` が入り直し、滞空が最大0.69秒延長される。
高速域では単発ジャンプの到達距離が **760px**（`singleRange` の上限）に達する一方、
足場の幅は次のとおり。

| 足場の種類 | 幅 | 出現率 |
|---|---:|---:|
| 通常 | 190〜430px | — |
| 極端に狭い足場 | 56〜102px | 7% |

**全開の2段目を撃つと、足場の幅を大きく超えて飛び、次の奈落へ落ちる。**
2段目を小さく撃てば滞空が縮み、足場の上へ降りられる。

つまりこの機能は「跳ぶ高さの調整」ではなく、**滞空時間＝着地点の調整**である。

#### そのため、4節の調整目標は単位が間違っている

カット率 `k` を掛けたときの関係は次のとおり。**高さと滞空時間は比例しない。**

| | 倍率 |
|---|---|
| 滞空時間 | `k` |
| 水平到達距離 | `k` |
| 到達高さ | **`k²`** |

4節は「小ジャンプの頂点は大ジャンプのおよそ55〜65%」を目標にしている。
これを満たす `k` は **0.74〜0.81** で、そのとき**水平距離は74〜81%までしか縮まない**。
用途2（760px跳ぶところを190〜430pxの足場へ収める）には**まったく足りない**。

一方、同じ4節が指定する `RELEASE CUT = 0.55` は、高さでは30%にしかならず、
「頂点55〜65%」という記載と**自己矛盾している**。

**結論: `RELEASE CUT = 0.55` を採用し、「頂点の55〜65%」という目標記述を削除する。**
調整目標は高さではなく、**滞空時間・水平到達距離で 50〜60%** と書き直すこと。
デバッグパネルの状態表示にも、到達高さだけでなく**滞空時間と水平到達距離**を出すと、
実機調整で正しい指標を見られる。

### 15.9 テスト時の注意

`loop()` 全体が `try/catch` で囲まれ、例外は `console.error('game loop error:', err)` を
出すだけでループが継続する。**画面は動いて見えるのに内部で例外が出続ける状態が起こりうる。**
Playwrightでは `page.on('console')` で `game loop error` を拾い、1件でも出たら失敗とすること。
