# HELL RUNNER 大ジャンプ・小ジャンプ機能 実装指示書

作成日: 2026-08-16  
状態: **実装前。別AIへ渡せる確定仕様**

## 1. 目的

現在の「押した瞬間に常に同じ高さまで跳ぶ」操作へ、押している長さで高さが変わる可変ジャンプを追加する。

- 短く押す: 小ジャンプ
- 押し続ける: 現在と同じ大ジャンプ

小さな段差やコイン列を細かく狙えるようにしつつ、既存の奈落・段差・2段ジャンプ・3段ジャンプ・滑空を壊さないことを最優先とする。

## 2. 採用方式

ジャンプ開始時の速度は、現在と同じ `-JUMP_VELOCITY` を与える。

上昇中にボタンを離した場合だけ、上向き速度を弱めて早めに頂点へ移行させる「ジャンプカット方式」を採用する。

概念例:

```js
// 毎フレーム、重力を加算する前に判定する（イベントではなく状態で見る。理由は5節）
if (jumpCanBeCut && player.vy < 0 && !holdingInput) {
  player.vy *= JUMP_RELEASE_CUT;
  jumpCanBeCut = false;
}
```

理由:

- 最大ジャンプは現状と同じ軌道を維持できる
- 地形生成が参照する `JUMP_VELOCITY`、`SINGLE_JUMP_APEX`、奈落幅を変更せずに済む
- 押した瞬間から反応するため、長押し時間を待ってから跳ぶ方式より操作遅延がない
- PCのキー入力と携帯のタップを同じ処理へ統一できる

## 3. 操作仕様

### 1段目

- pointerdown / Space / ↑ / W のkeydownで、従来どおり即座にジャンプする
- 上昇中にすぐ離すと小ジャンプ
- 押し続けると現在と同じ最大高度の大ジャンプ
- 頂点を越えて落下へ入った後に離しても軌道を変えない

### 2段目・3段目

- 空中で再度押した瞬間に、従来どおり次のジャンプを発動する
- 2段目と、レッドブル選択時の3段目にも同じ大小判定を適用する
- 新しいジャンプを開始するたび、そのジャンプ専用の押下状態へ切り替える
- 1段目のボタンを押し続けただけで2段目を自動発動させない

### 滑空

- 滑空の既存条件「滑空能力を持ち、落下中に入力を押し続けている」を維持する
- 同じ長押し操作が、上昇中は大ジャンプ、落下中は滑空として自然につながる
- 小ジャンプ後に滑空したい場合は、一度離して小ジャンプを確定し、落下中にもう一度押す
- 滑空の重力倍率 `0.32` は今回変更しない
- 可変ジャンプの追加を理由に、滑空能力の解放距離・選択仕様を変更しない

#### 大ジャンプと滑空が同じ操作になる件（ユーザー確定済み・2026-08-16）

滑空は `gliding = abilities.glide && holdingInput && player.vy > 0` で発動する。
つまり**滑空能力を持つプレイヤーが大ジャンプ（押し続け）をすると、頂点を越えた瞬間に
必ず滑空へ入る**。大ジャンプと滑空が同じ「長押し」に割り当たる構造になる。

**これを仕様として確定する。** 判断は以下のとおり。

- 長押しの大ジャンプから、**そのまま自動的に滑空へつながってよい**
- 大ジャンプだけして滑空したくない場合は、**頂点付近で指を離す**操作とする

滑空持ちにとって「大ジャンプ＋滑空」が既定の挙動になり、滑空を切りたい時だけ
指を離す。一連の長押しが「上昇→滞空延長」として一貫するため、これを自然な設計とみなす。
**入力を分ける仕組みは追加しない。**

## 4. 初期調整値

最終値はデバッグモードの実機試遊で決める。最初の候補値は以下。

| 項目 | 定数名 | 初期候補 | 意味 |
|---|---|---:|---|
| 最大ジャンプ速度 | `JUMP_VELOCITY` | 現在値(1180) | 大ジャンプと既存地形を維持。変更しない |
| リリースカット率 | `JUMP_RELEASE_CUT` | `0.55` | 上昇中に離した時、その時点の上向き速度へ掛ける係数 |

**調整すべき数値はこの1つだけ。時間による閾値も、速度の下限も置かない。**
かつてここには「最低カット受付時間 0.04秒」と「最大ジャンプ到達扱い 0.18秒」があったが、
どちらも削除した。理由は5節に記す。

速度の下限も不要。上昇中に常にカットする方式なら、**最小ジャンプは即離し時の
62px で自然に決まる**ためで、これを別の仕組みで守る必要がない。

### 目標感触

**調整の基準は「高さ」ではなく「滞空時間」と「水平到達距離」。** 理由は7節を参照。

- 即座に離した最小ジャンプで、滞空・水平距離が大ジャンプの **50〜60%**
- 大ジャンプの高さ・滞空時間・到達距離は現状から変えない
- 最小ジャンプでも、ジャンプ不要な段差(`STEP_AUTO_MAX` = 34px)より明確に高く跳べる
- 携帯Safariでタップ時間がばらついても大小を意図的に出し分けられる

### 参考: 現行物理値から計算した実測値

`GRAVITY = 3400`、`JUMP_VELOCITY = 1180` のとき、大ジャンプは
**滞空0.694秒 / 最高到達204.8px / 頂点まで0.347秒**。

`JUMP_RELEASE_CUT = 0.55` で、離す時刻ごとの実際の比率は次のとおり。

| 離す時刻 | 滞空 | 水平距離 | 高さ |
|---:|---:|---:|---:|
| 0.00秒(即離し) | 55% | 55% | 30% |
| 0.10秒 | 74% | 74% | 65% |
| 0.20秒 | 87% | 87% | 87% |
| 0.30秒 | 97% | 97% | 99% |

**小ジャンプとして意味を持つのは0〜0.1秒の範囲だけで、それ以降はほぼ大ジャンプになる。**
比率は離す時刻で連続的に変わるため、単純な数式では表せない。
**上表は目安であり、確定はデバッグモードの実測値で行う（8節）。**

### カット率の下限

`JUMP_RELEASE_CUT` を下げすぎると最小ジャンプが `STEP_AUTO_MAX`(34px) を下回り、
「跳ばなくても越えられる段差」より低くなって存在意義を失う。

即離し時の高さは `JUMP_RELEASE_CUT²` × 204.8px なので、
**`0.45` を下回らないこと**(0.45で41px、0.55で62px)。

## 5. 状態管理

### イベントではなく状態で判定する

**「離した瞬間」を捉えるイベント方式を採らない。** 毎フレームの物理更新で
「今ボタンが押されていないか」を見る状態方式にする。**この選択が仕様の要。**

理由。ジャンプはイベントハンドラでは発動せず、`update()` 内の
`if(jumpQueued){ ... player.vy = -JUMP_VELOCITY; ... }` で**次フレームに発動する**。
そのため素早いタップでは実行順が

```
pointerdown（jumpQueued = true）→ pointerup → update()（ここで初めてジャンプ開始）
```

となる。**ジャンプが始まる前に指が離れている。** イベント方式で「離した」を予約しても、
ジャンプ開始時にその予約を初期化してしまえば消える。結果、**一番速いタップが
一番大きく跳ぶ**という、狙いと正反対の挙動になる。

状態方式なら、ジャンプ開始の次のフレームで `holdingInput === false` を見て
即座にカットが効くため、実行順に左右されない。

### 持つ状態

- `jumpCanBeCut`: 今の上昇へリリースカットを適用できるか（1回のジャンプにつき1度だけ）

**これだけでよい。** `jumpHeldTime` と `jumpReleaseQueued` は物理には不要。
押下時間はデバッグ表示のためだけに計測してよいが、**判定には使わない**。

### ジャンプ開始時（`jumpQueued` を消費する箇所）

```js
player.vy = -JUMP_VELOCITY;
jumpCanBeCut = true;   // この上昇はカット可能
```

### 毎フレーム、重力を加算する前に判定する

```js
// 上昇中に手を離していたらカットする。
// 「離した瞬間」のイベントではなく毎フレームの状態で見るのは、素早いタップだと
// ジャンプ開始より先に pointerup が来てしまい、イベントでは取りこぼすため。
if(jumpCanBeCut && player.vy < 0 && !holdingInput){
  player.vy *= JUMP_RELEASE_CUT;
  jumpCanBeCut = false;
}
```

**時間の閾値を置かないのは、この式が自然に滑らかだから。** 頂点へ近づくほど
`player.vy` は0に近づくので、遅く離すほどカットの影響は自動的に小さくなる。
逆に「0.18秒を超えたらカットしない」のような閾値を置くと、
**0.179秒と0.181秒で到達高度が急変する**不連続が生まれる。

### カット権を終了する条件

- カットを適用した
- 頂点へ到達して `player.vy >= 0` になった
- 着地した
- 次の空中ジャンプを開始した（新しいジャンプは新しいカット権を持つ）
- 死亡、転生、デバッグ復帰、ゲーム開始、TOPへ戻る

### 一時停止との関係

判定に時間を使わないため、**一時停止中に押下時間が進む問題はそもそも起きない**。
`paused` / `pauseCountdown` 中は `update()` 自体を走らせないので、カット判定も止まる。
再開時は `holdingInput` を false にしておくこと（一時停止指示書5節と同じ扱い）。

## 6. 入力イベント

既存の入力方式を維持する。

- `pointerdown`: `holdingInput = true`、従来の `requestJump()`
- `pointerup`: `holdingInput = false`
- `pointercancel`: pointerupと同じ扱い
- `keydown`: Space / ↑ / W。**`e.repeat` ガードは追加済み**（本体修正済み。触らない）
- `keyup`: 対応キーを離したら `holdingInput = false`
- `touchstart` / `touchmove` の既存 `preventDefault()` を壊さない

**「ジャンプリリースを予約する」仕組みは作らない。** 入力側がやるのは `holdingInput` の
更新だけで、カットの判定は物理更新側が毎フレーム状態を見て行う（5節）。
予約フラグを挟むと、ジャンプ開始時の初期化で取りこぼす経路が生まれる。

追加注意:

- ボタン、リンク、デバッグUI、一時停止UIの操作をジャンプへ混ぜない
- ウィンドウが非表示になった場合は入力を解除し、復帰直後に大ジャンプ・滑空が残らないようにする
- 一時停止機能が先に実装されている場合、`paused` と `pauseCountdown` 中の入力を無視する
- 一時停止機能がまだ未実装でも、後から統合しやすいよう入力解除処理を関数化する

## 7. 地形・難易度を維持する条件

- `JUMP_VELOCITY` と `GRAVITY` の本番初期値は変更しない
- `SINGLE_JUMP_APEX` と奈落生成上限を変更しない
- 既存の単発ジャンプ・2段ジャンプで到達可能だった地形は、大ジャンプ操作で引き続き到達可能にする
- 小ジャンプを必須にしない。小ジャンプは操作精度を上げる追加手段とする
- 大ジャンプを最大まで出すために不自然な長押しを要求しない
- ライバルAIのジャンプは現状の固定ジャンプを維持する。プレイヤー用のリリースカットを適用しない
- コイン配置や能力解放条件は今回変更しない

## 8. デバッグモードへ追加する調整機能

同じ数値を繰り返し変更せず実機で決められるよう、`?debug=1` のDEV TOOLSへ `JUMP HEIGHT` セクションを追加する。

### 必須コントロール

1. `RELEASE CUT`
   - 範囲: `0.45～0.90`（下限の根拠は4節）
   - step: `0.01`
2. `COPY JUMP VALUES`

**スライダーはこの1つだけ。** `MIN HOLD` と `FULL HOLD` は5節で時間閾値を廃止したため作らない。

### 状態表示

**理論値ではなく、直近のジャンプを実測した値を出す。** カット後の挙動は離した時刻で
連続的に変わり、単純な数式では表せないため、**計測値だけが調整の根拠になる**。

直近のジャンプについて、以下を実測して表示する。

| 表示 | 内容 |
|---|---|
| `AIRTIME` | 踏切から着地までの実滞空時間（秒）と、大ジャンプ比(%) |
| `DISTANCE` | その間に進んだ実水平距離（px）と、大ジャンプ比(%) |
| `HEIGHT` | 実際の最高到達高度（px）と、大ジャンプ比(%) |
| `JUMPS` | 現在のジャンプ段数 |
| `MODE` | `SMALL` / `FULL` / `GLIDE` の現在判定 |

比較基準となる「大ジャンプ」の値は、**カットを一度も適用しなかったジャンプの実測値**を
保持して使う。起動直後で基準が無い間は理論値（滞空0.694秒 / 204.8px）を仮に用いる。

押下時間も参考として表示してよいが、**判定には使っていない**ことを明記すること
（見た人が「押下時間で分岐している」と誤解しないため）。

### 公開範囲

- 通常URLへ調整パネルを表示しない
- 通常URLで `window` へ調整APIを公開しない
- デバッグ値は本番記録や能力解放へ影響させない
- 確定後は本番定数へ反映し、デバッグ初期値も同じ値へ揃える

`tests/debug-mode.spec.js` へ、最低限以下を追加する。

   （時間閾値を廃止したため、特定の時刻を境に急変してはならない）
5. 短押しと長押しの両方で着地でき、ジャンプ回数が正常にリセットされる

7. **高速域で2段目を短く撃つと、全開で撃つより手前へ着地する**（用途2の担保）
8. 2段目を短押し／長押しで出し分けられる
9. レッドブル選択時の3段目にも大小判定が適用される
10. 長押しだけで2段目・3段目が自動発動しない
11. 滑空未解放時は落下中の長押しで滑空しない

13. pointercancel後に長押し状態が残らない
14. キーリピートでジャンプ回数を余分に消費しない（本体は修正済み。挙動を固定するテスト）
15. 小ジャンプ追加後も既存の奈落を大ジャンプ＋空中ジャンプで越えられる
16. 390×844の携帯相当で短押し・長押し入力が動く

| `k` に対する滞空・距離・高さの比は即離し時のみの近似 | 4節・8節 | 実測値で調整する方針を明記。デバッグ表示を実測へ変更 |
| 大ジャンプと滑空が同じ長押しに割り当たる | 3節 | 「そのまま滑空へつながる」でユーザー確定 |
| `keydown` にキーリピート対策が無い | — | **本体へ修正済み（コミット `6013295`）。再実装しないこと** |

### 15.2 【要注意】既存プレイヤーの操作感が変わる

現在は**どんなタップでも204.8px跳ぶ**。変更後、即離しは62pxになる。
地形の段差は最大132px（`STEP_MAX_H`）あるため、**軽いタップでは越えられない段差が出る**。

7節は「小ジャンプを必須にしない」としているが、問題は必須かどうかではなく
**同じ入力が別の結果を生むこと**。既存プレイヤーの指の癖はそのままなので、
変更直後は明らかに死にやすくなる。

実機調整では、まず `RELEASE CUT` を高め（`0.70` 程度）から始めて段階的に下げ、
**どこから「今までどおり跳べない」と感じるか**を確認するとよい。

### 15.3 【携帯】マルチタッチで意図せずジャンプがカットされる

`pointerup` は指を1本離しただけで発火し、`holdingInput = false` になる。
現状でも滑空が途切れる問題があるはずだが、可変ジャンプでは
**2本目の指を離しただけで上昇が切られる**ため、影響が大きくなる。

押されているポインタ数を数えて `holdingInput` を管理する方式を検討すること
（6節の「入力解除処理を関数化する」と合わせて対応できる）。

### 15.4 実装アンカー（確認済みの事実）

| 項目 | 実測 |
|---|---|
| 符号 | `vy < 0` が上昇、`vy > 0` が落下。2節のコード例は正しい |
| ジャンプ発動位置 | `update()` 内の `if(jumpQueued){...}` ブロック。**イベントハンドラではない**。`jumpCanBeCut = true` の初期化はここへ置く |
| 着地処理 | 同じく `update()` 内。`player.jumpsUsed = 0` で回数が戻る（用途1の根拠） |
| 3段ジャンプ | `maxJumpsThisRun = abilities.redbull ? 3 : 2` で実在 |
| 滑空 | `gliding = abilities.glide && holdingInput && player.vy > 0` / 重力倍率 `0.32`。変更しない |
| キー | `' '` / `ArrowUp` / `w` / `W` の keydown・keyup が実在。`e.repeat` ガードは追加済み |
| 地形 | 足場の幅は通常190〜430px、狭い足場は56〜102px（出現率7%）。高速域の単発ジャンプ到達距離は上限760px |
| 段差 | `STEP_AUTO_MAX = 34px`（跳ばずに越えられる）、`STEP_MAX_H = 132px`（最大） |
| ライバルAI | プレイヤーとは別処理。`holdingInput` を見ないため、7節の「固定ジャンプ維持」は自動的に満たされる |

### 15.5 テスト時の注意

`loop()` 全体が `try/catch` で囲まれ、例外は `console.error('game loop error:', err)` を
出すだけでループが継続する。**画面は動いて見えるのに内部で例外が出続ける状態が起こりうる。**
Playwrightでは `page.on('console')` で `game loop error` を拾い、1件でも出たら失敗とすること。
